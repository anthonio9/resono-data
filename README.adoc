= resono-data
:toc: left
:source-highlighter: highlight.js

Dataset downloading, preprocessing, and PyTorch DataLoaders for guitar pitch recognition.
Importable as `resono.data` - a namespace package designed to sit alongside the `resono` model repository.

== Installation

[source,bash]
----
pip install -e .
----

== GuitarSet pipeline

Run the three steps in order.
All paths default to `data/raw`, `data/cache`, and `data/partitions` relative to your working directory.

=== 1. Download

Downloads audio and annotation archives from Zenodo (≈ 1.5 GB).
Skips files that already exist.

[source,bash]
----
python -m resono.data.datasets.guitarset download
----

=== 2. Preprocess

Resamples audio and extracts per-string pitch arrays from JAMS annotations into `.npy` files.

[source,bash]
----
python -m resono.data.datasets.guitarset preprocess
----

[cols="2,1,4", options="header"]
|===
| Flag | Default | Description
| `--sample-rate` | `22050` | Target sample rate in Hz
| `--hop-size` | `256` | Audio samples per pitch frame (~11.6 ms at 22050 Hz)
| `--raw-dir` | `data/raw` | Location of downloaded archives
| `--cache-dir` | `data/cache` | Output directory for `.npy` files
|===

=== 3. Partition

Writes `data/partitions/guitarset.json` with train/valid/test stem lists.

[source,bash]
----
python -m resono.data.datasets.guitarset partition
----

By default uses a player-based split: players `00`–`03` → train, `04` → valid, `05` → test.
This prevents player identity from leaking across splits.

To use a random 70/15/15 split instead:

[source,bash]
----
python -m resono.data.datasets.guitarset partition --no-player-split
----

==== Cross-validation folds (optional)

Writes six `guitarset_fold{0-5}.json` files, each rotating a different player into the test role:

[source,bash]
----
python -m resono.data.datasets.guitarset cv-folds
----

== GAPS pipeline

14 hours of classical (nylon-string) guitar, 300 performances by 200+ performers, labelled from aligned scores rather than from a pickup.

[source,bash]
----
python -m resono.data.datasets.gaps download      # ~11 GB; --no-audio for annotations only
python -m resono.data.datasets.gaps preprocess
python -m resono.data.datasets.gaps partition
----

Preprocessing writes the same three files as GuitarSet plus `{stem}-onset.npy`, a bool `(6, N_frames)` array marking note-start frames. Voicing transitions cannot mark a re-struck note of the same pitch on the same string; this can.

=== Where the labels come from

No single GAPS annotation is sufficient, so preprocessing combines three:

[cols="1,2,2"]
|===
| Source | Supplies | Cannot supply

| MusicXML | pitch, string, fret, tuning | any performance time
| syncpoints | measure downbeats in seconds (~1.3 per measure) | anything finer than a measure
| fine-aligned MIDI | per-note onset and offset in seconds | string — every note is on channel 0
|===

Onsets therefore come from the MIDI, string labels from the MusicXML tablature, and the syncpoints supply the measure-level time prior that links them. Interpolating onsets from syncpoints alone lands a median 215-434 ms from the MIDI's — 18 to 37 frames at a 256-sample hop — so the MIDI is what makes frame-accurate labels possible.

Because the MIDI carries no string information, transferring the score's string labels onto performance timing requires an alignment step. Repeats are expanded first (performers take repeats the score writes once), and the syncpoint count cross-checks that expansion.

=== Known limitations

* *String labels are approximate and unvalidated.* GAPS has no per-string ground truth, so their accuracy cannot be measured on this dataset. Roughly 6-9% of notes get no confident score match and fall back to a lowest-playable-fret heuristic. The dataset's own `.match` files pair only 18-28% of performed notes and are not a usable reference.
* *Offsets are the weakest labels.* The GAPS authors evaluate onsets only, without offsets, so note durations — and hence voiced-region ends — are less reliable than onsets.
* *Pitch is piecewise constant.* Labels come from the score, so GAPS contains no bends or vibrato. It is detection data, not continuous-f0 data.
* *The official test split leaks performers.* It is a random 90:10 split by piece; 12 performers appear in both train and test. Validation is carved out by performer, which fixes train/valid but not train/test.
* *Tablature is editorial fingering* and need not match what the performer actually played.
* *No tuning-offset correction.* The authors' filter used a ±50-cent tolerance, which passes 20-30 cent offsets.

GAPS is distributed for non-commercial research use only and should not be redistributed; see https://aim-qmul.github.io/GAPS/. The HuggingFace mirror's MIT tag conflicts with those terms.

== Usage in Python

[source,python]
----
from resono.data import get_loader

loader = get_loader(
    datasets=["guitarset"],
    partitions_dir="data/partitions",
    cache_dir="data/cache",
    split="train",
    hop_size=256,
    window_frames=32,   # frames per batch item (~370 ms)
    batch_size=32,
)

for batch in loader:
    audio  = batch["audio"]   # (B, window_frames * hop_size)  float32
    pitch  = batch["pitch"]   # (B, 6, window_frames)           float32, Hz
    voiced = batch["voiced"]  # (B, 6, window_frames)           bool
    stem   = batch["stem"]    # list[str], track identifier
----

=== Sampling modes

Training loaders draw only from pre-filtered index pools, so the model never trains on silent chunks.

[cols="2,4", options="header"]
|===
| Mode | Behaviour
| `voiced_idx` (default) | Samples any frame where at least one string is active. Covers onsets, sustained notes, and everything in between.
| `onset_idx` | Restricts sampling to frames where at least one string transitions from unvoiced to voiced. Useful for onset-focused training. Enable with `use_onset_idx=True`.
|===

Both modes use `window_frames` consecutive frames per item.
Setting `window_frames=1` gives single-frame recognition.

Validation and test loaders use sequential non-overlapping chunks covering every track in full, including silent regions, so predictions can be reconstructed track by track.

== Adding a new dataset

=== 1. Implement the three pipeline functions

Create `src/resono/data/datasets/<name>/` with at least:

`download.py` — `download(raw_dir: Path) -> None`::
  Fetch raw files from the source. Skip files that already exist.

`preprocess.py` — `preprocess(raw_dir: Path, cache_dir: Path, **kwargs) -> None`::
  Convert raw files to `.npy` arrays under `cache_dir/<name>/`.
  Each track must produce three files:
+
[source]
----
{stem}-audio.npy   float32  (N_samples,)
{stem}-pitch.npy   float32  (6, N_frames)   Hz, 0.0 = unvoiced
{stem}-voiced.npy  bool     (6, N_frames)
----

`partition.py` — `partition(cache_dir: Path, partitions_dir: Path, **kwargs) -> None`::
  Write `partitions_dir/<name>.json`:
+
[source,json]
----
{"train": ["stem_a", ...], "valid": ["stem_b", ...], "test": ["stem_c", ...]}
----

Optionally subclass `resono.data.datasets.base.DatasetModule` to get static type checking on the interface.

=== 2. Register the dataset

Add it to `src/resono/data/datasets/__init__.py`:

[source,python]
----
from resono.data.datasets import guitarset, <name>

REGISTRY = {
    "guitarset": guitarset,
    "<name>": <name>,
}
----

Once registered, the dataset can be passed to `get_loader(datasets=["<name>", ...])`.
