= resono-data
:toc: left
:source-highlighter: highlight.js

Dataset downloading, preprocessing, and PyTorch DataLoaders for guitar pitch recognition.
Importable as `resono.data` - a namespace package designed to sit alongside the `resono` model repository.

== Installation

[source,bash]
----
pip install -e .
----

== GuitarSet pipeline

Run the three steps in order.
All paths default to `data/raw`, `data/cache`, and `data/partitions` relative to your working directory.

=== 1. Download

Downloads audio and annotation archives from Zenodo (≈ 1.5 GB).
Skips files that already exist.

[source,bash]
----
python -m resono.data.datasets.guitarset download
----

=== 2. Preprocess

Resamples audio and extracts per-string pitch arrays from JAMS annotations into `.npy` files.

[source,bash]
----
python -m resono.data.datasets.guitarset preprocess
----

[cols="2,1,4", options="header"]
|===
| Flag | Default | Description
| `--sample-rate` | `22050` | Target sample rate in Hz
| `--hop-size` | `256` | Audio samples per pitch frame (~11.6 ms at 22050 Hz)
| `--raw-dir` | `data/raw` | Location of downloaded archives
| `--cache-dir` | `data/cache` | Output directory for `.npy` files
|===

=== 3. Partition

Writes `data/partitions/guitarset.json` with train/valid/test stem lists.

[source,bash]
----
python -m resono.data.datasets.guitarset partition
----

By default uses a player-based split: players `00`–`03` → train, `04` → valid, `05` → test.
This prevents player identity from leaking across splits.

To use a random 70/15/15 split instead:

[source,bash]
----
python -m resono.data.datasets.guitarset partition --no-player-split
----

==== Cross-validation folds (optional)

Writes six `guitarset_fold{0-5}.json` files, each rotating a different player into the test role:

[source,bash]
----
python -m resono.data.datasets.guitarset cv-folds
----

=== String ordering

Hex channel `c` carries string `c`, low E first — the same order as the JAMS `pitch_contour` annotations and as resono's own string axis.

*This is stated nowhere upstream*: not in the filenames (one 6-channel wav per track), the Zenodo record, the GuitarSet website, the ISMIR paper, or the JAMS metadata (which labels the six annotations only `'0'`–`'5'`).
It was established by measurement, and the pipeline hardcodes the result.

The annotation side is inferable from the data: the six annotations' notes start at MIDI 44, 51, 58, 62, 65, 72 — each at or above its open-string pitch (E2=40, A2=45, D3=50, G3=55, B3=59, E4=64), so index 0 is the low E.
The paper's Figure 1 legend agrees, reading `E — A — D — G — B — e`.

The audio side was measured directly.
For each track, for every frame the annotation marks string `s` voiced at frequency `f`, the CQT magnitude of each channel at `f` was compared across channels; the loudest channel is that string's.
Across 24 tracks spanning all six players and four genres, 19 gave the identity on every measurable string.
The five exceptions were all the same artefact, not a reordering: string 5 mapping to channel 2 on tracks where the high e plays exactly an octave above the D string (86% of shared frames within 30 cents of 1200), so the D string's 2nd harmonic lands on the high e's fundamental and outweighs it.
Those results are also not permutations — channel 2 claims two strings at once — which is the signature of a confused measurement rather than a genuine channel swap.

Since GuitarSet is a frozen Zenodo record, this cannot change, so no runtime check is kept.

=== Sharp keys: `#` is renamed to `sharp` on extraction

GuitarSet track IDs encode the key, and 48 of the 360 tracks are in a sharp key — `00_Funk3-112-C#_comp`.

That `#` is hostile to tooling. Kaggle rejects it in filenames outright, so re-hosted copies of these archives circulate with `Csharp` instead of `C#`.
A raw tree assembled from a mixture of the two spellings is the dangerous case: the pipeline joins audio to annotations by filename, and a track whose spellings disagree simply never appears in the index.
It is dropped with no error at all.

Every archive is therefore unpacked through `guitarset.download.extract_and_rename_sharp()`, which rewrites `#` to `sharp` in member names as it writes them.
Both `guitarset` and `reguitarset` extract this way, so the on-disk layout is self-consistent whatever spelling an archive arrived with, and nothing downstream needs to know the discrepancy exists.

If you have a raw tree from before this was in place, rename the stragglers once:

[source,bash]
----
python -c "
from pathlib import Path
for p in Path('data/raw/guitarset').rglob('*#*'):
    p.rename(p.with_name(p.name.replace('#', 'sharp')))
"
----

== GAPS pipeline

14 hours of classical (nylon-string) guitar, 300 performances by 200+ performers, labelled from aligned scores rather than from a pickup.

[source,bash]
----
python -m resono.data.datasets.gaps download      # ~11 GB; --no-audio for annotations only
python -m resono.data.datasets.gaps preprocess
python -m resono.data.datasets.gaps partition
----

Preprocessing writes the same three files as GuitarSet plus `{stem}-onset.npy`, a bool `(6, N_frames)` array marking note-start frames. Voicing transitions cannot mark a re-struck note of the same pitch on the same string; this can.

=== Where the labels come from

No single GAPS annotation is sufficient, so preprocessing combines three:

[cols="1,2,2"]
|===
| Source | Supplies | Cannot supply

| MusicXML | pitch, string, fret, tuning | any performance time
| syncpoints | measure downbeats in seconds (~1.3 per measure) | anything finer than a measure
| fine-aligned MIDI | per-note onset and offset in seconds | string — every note is on channel 0
|===

Onsets therefore come from the MIDI, string labels from the MusicXML tablature, and the syncpoints supply the measure-level time prior that links them.

Two questions come up every time, and both are settled by measurement:

*"The MusicXML already has the strings — why involve the MIDI?"* Because MusicXML has no seconds, only measures and divisions. Interpolating onsets from syncpoints instead assumes the performer played metronomically within each bar; measured against the MIDI's real onsets that lands a median *215-434 ms* out, which is *18 to 37 frames* at a 256-sample hop. Only 0.3-6.2% of onsets fall within a single frame.

*"Aren't the syncpoints per beat?"* No, per measure — a median 1.34 anchors per measure across the 300 tracks, and 1.20 for 4/4 pieces rather than 4.0. The GAPS paper says they aligned "at measure level ... so that any alignment errors would be localised to one measure".

=== How the alignment works

Because the MIDI carries no string information, the score's string labels have to be transferred onto performance timing. Repeats are unfolded first, since performers take repeats the score writes once.

Neither obvious approach works alone. Matching by *note order* is defeated by repeats and, more stubbornly, by chord members having no canonical order on either side — an LCS, the theoretical ceiling for any order-based match, gets no further. Matching by *interpolated time* works well where syncpoints are dense and collapses where they are sparse.

So the module combines them: a monotonic dynamic program in which a pair may match only if the pitches are equal and the MIDI onset lies within a tolerance of the score note's syncpoint-predicted time, with the reward decaying linearly in that time error. The syncpoints act as a prior that disambiguates between same-pitch candidates; the monotonicity prevents a note matching an identical pitch elsewhere in the piece. Both sequences are sorted by (time, pitch) first, which is what neutralises the chord-ordering problem.

Notes left unmatched fall back to a heuristic: the lowest fret playable on a string not already sounding, using the tuning declared in the score.

=== What actually survives

Measured across all 300 split tracks:

[cols="1,1,1,1"]
|===
| | Tracks | Median coverage | Mean

| included | *214* | *98.0%* | 93.9%
| excluded | *86* | 62.9% | 62.5%
|===

"Coverage" is the share of MIDI notes receiving a string from the score, so it measures completeness, not correctness — see the limitations below.

Every exclusion comes from one cross-check: syncpoint indices are performed measure numbers, so they independently state how many measures exist, and on 86 tracks that disagrees with the score by more than one. The 28-point coverage gap is the reason to trust that check rather than treat it as arbitrary — it selects tracks that demonstrably align worse.

=== Known limitations

* *About a quarter of GAPS is excluded by default.* On 86 of the 300 tracks the score and the syncpoints disagree on how many measures were performed, always with the syncpoints claiming more. Which side is wrong is unresolved. Those tracks align far worse than the rest (median coverage 62.9% against 98.0%), so they are dropped; `--keep-measure-mismatch` retains them for investigation. `manifest.json` in the cache records what was kept and why each of the rest was not.
* *String labels are approximate and unvalidated.* GAPS has no per-string ground truth, so their accuracy cannot be measured on this dataset. On included tracks a median 2% of notes get no confident score match and fall back to a lowest-playable-fret heuristic; the spread is wide, and 13 included tracks still sit below 70% coverage for reasons that remain unexplained. The dataset's own `.match` files pair only 18-28% of performed notes and are not a usable reference.
* *Offsets are the weakest labels.* The GAPS authors evaluate onsets only, without offsets, so note durations — and hence voiced-region ends — are less reliable than onsets.
* *Pitch is piecewise constant.* Labels come from the score, so GAPS contains no bends or vibrato. It is detection data, not continuous-f0 data.
* *The official test split leaks performers.* It is a random 90:10 split by piece; 12 performers appear in both train and test. Validation is carved out by performer, which fixes train/valid but not train/test.
* *Tablature is editorial fingering* and need not match what the performer actually played.
* *No tuning-offset correction.* The authors' filter used a ±50-cent tolerance, which passes 20-30 cent offsets.

GAPS is distributed for non-commercial research use only and should not be redistributed; see https://aim-qmul.github.io/GAPS/. The HuggingFace mirror's MIT tag conflicts with those terms.

== Inspecting labels against audio

Plots the preprocessed labels over the audio they describe, to check by eye that ground truth lands where the notes actually are.
Reads the `.npy` cache, so it works for any dataset — the cache format is shared.

Needs matplotlib: `pip install -e '.[viz]'`.

[source,bash]
----
python -m resono.data plot --dataset guitarset --list-stems
python -m resono.data plot --dataset gaps --stem 001_mvswc --start 40 --duration 8
python -m resono.data plot --dataset gaps --stem 001_mvswc --theme dark --output plot.png
----

`--list-stems` prints the dataset's cached tracks with their duration and whether onset labels are present.
Omitting `--stem` plots the first cached track.

The upper panel draws the labelled pitch over a constant-Q spectrogram: CQT bins are logarithmic in frequency like pitch itself, so a correct label sits on the fundamental with its harmonics stacked evenly above.
A linear STFT would crowd the low strings into a few pixels and hide exactly the errors worth seeing.
The lower panel gives each string its own labelled lane — six categorical colours cannot be told apart reliably where they overlap, so strings are separated by position instead, and the lane label reports the pitch range observed rather than an assumed tuning.

Onsets are drawn where the dataset provides them; GuitarSet has no onset file, and the title says so rather than leaving a silent absence.

== Usage in Python

[source,python]
----
from resono.data import get_loader

loader = get_loader(
    datasets=["guitarset"],
    partitions_dir="data/partitions",
    cache_dir="data/cache",
    split="train",
    hop_size=256,
    window_frames=32,   # frames per batch item (~370 ms)
    batch_size=32,
)

for batch in loader:
    audio  = batch["audio"]   # (B, window_frames * hop_size)  float32
    pitch  = batch["pitch"]   # (B, 6, window_frames)           float32, Hz
    voiced = batch["voiced"]  # (B, 6, window_frames)           bool
    stem   = batch["stem"]    # list[str], track identifier
----

=== Sampling modes

Training loaders draw only from pre-filtered index pools, so the model never trains on silent chunks.

[cols="2,4", options="header"]
|===
| Mode | Behaviour
| `voiced_idx` (default) | Samples any frame where at least one string is active. Covers onsets, sustained notes, and everything in between.
| `onset_idx` | Restricts sampling to frames where at least one string transitions from unvoiced to voiced. Useful for onset-focused training. Enable with `use_onset_idx=True`.
|===

Both modes use `window_frames` consecutive frames per item.
Setting `window_frames=1` gives single-frame recognition.

Validation and test loaders use sequential non-overlapping chunks covering every track in full, including silent regions, so predictions can be reconstructed track by track.

== Adding a new dataset

=== 1. Implement the three pipeline functions

Create `src/resono/data/datasets/<name>/` with at least:

`download.py` — `download(raw_dir: Path) -> None`::
  Fetch raw files from the source. Skip files that already exist.

`preprocess.py` — `preprocess(raw_dir: Path, cache_dir: Path, **kwargs) -> None`::
  Convert raw files to `.npy` arrays under `cache_dir/<name>/`.
  Each track must produce three files:
+
[source]
----
{stem}-audio.npy   float32  (N_samples,)
{stem}-pitch.npy   float32  (6, N_frames)   Hz, 0.0 = unvoiced
{stem}-voiced.npy  bool     (6, N_frames)
----

`partition.py` — `partition(cache_dir: Path, partitions_dir: Path, **kwargs) -> None`::
  Write `partitions_dir/<name>.json`:
+
[source,json]
----
{"train": ["stem_a", ...], "valid": ["stem_b", ...], "test": ["stem_c", ...]}
----

Optionally subclass `resono.data.datasets.base.DatasetModule` to get static type checking on the interface.

=== 2. Register the dataset

Add it to `src/resono/data/datasets/__init__.py`:

[source,python]
----
from resono.data.datasets import guitarset, <name>

REGISTRY = {
    "guitarset": guitarset,
    "<name>": <name>,
}
----

Once registered, the dataset can be passed to `get_loader(datasets=["<name>", ...])`.
